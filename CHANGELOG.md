The block maps `/seo-genius:<skill>`, `/mcp`, and `${CLAUDE_PLUGIN_ROOT}` (the installed plugin folder, for the ledger script) to Codex. The guide says the pipeline needs Node.js and an interactive session, since `codex exec` refuses every write, `save_plan_items` included. A release bumps the version in `.codex-plugin/plugin.json` with `plugin.json`; `scripts/check.mjs` fails when they differ.
- Tests: `tests/check/codex-pack.test.mjs` pins the pack's manifest, MCP entry, config entry, AGENTS block, and guide.
- New skill `citations` (#22): a NAP check of the business's Google Business Profile and of the US business directories in the Yext and BrightLocal networks, through the server's `citation_check` tool (seo-genius-workflows #358). The server reads the profile through Google's Business Information API with the business's own connected account, read only, and web search results (URL, title, snippet); it opens no directory page. Each directory reads NAP matches, formatting differs, fix this listing (field and value found), partly confirmed, listing seen with the NAP not shown, not seen in search ("Check by hand before creating a listing"), or not checked this run, each with a link to check by hand. It never calls a directory "not listed".
- `citations` checks that `citation_check` is in the tool list before it asks anything, confirms the NAP, asks once about other names, numbers and old addresses, offers a saved report from the last 30 days, and states the cost before a fresh check: up to 80 paid searches plus 37 per other name and one per old address. The server reserves the most a run could cost and keeps only what it spent, in units that follow its search engine: on Firecrawl, its usual engine, 268 units reserved (plus 130 per other name and 4 per old address) and 1 unit plus the credits used kept; on the Data-for-SEO fallback, 2,000 reserved (plus 925 and 25) and 1 unit plus 25 per search that ran kept. A smaller `max_queries` reserves the same and only gets a bigger refund. A refusal before the check starts (plan, paused, archived or unverified site, monthly quota) costs nothing; a run already in progress, the daily spend limit, or an error during the run keeps 1 unit. It never passes `max_seconds` above 45, the server's default, which fits a client that stops waiting at 60 seconds.
- `citations` names every directory not checked this run and says why (time or search budget, provider failures, or a server whose search engine checks part of the list), and never counts one as not seen or missing. The not-seen group names the major and aggregator directories and counts the rest by tier. The free-plan refusal, the one-run-per-business 409, the paused-site 409, the archived and unverified replies (returned, not thrown), the monthly-quota and per-minute 429s, and the spend-ceiling 503 each have their own message.
- `citations` saves its report through the ledger (`research/citations-<date>.md` and `.json`, one `save`), and to SEO Genius as a `citation_audit` research document only after the user says yes. It carries the shared Unattended runs block: an unattended run calls `citation_check` only when the config's `unattended` block says `"citation_check": true`, counting each search it may run toward `live_calls_per_run`, and never saves to the server.
- The structural checker expects nineteen skills and `citations` among the Unattended runs skills. The Codex AGENTS block lists `citation_check` with the tools that spend quota, and the Codex guide lists `citations` with the skills that need Node.js. Tests: `tests/check/citations.test.mjs`.

- `competitor-dive` records a term with no reading from this run (skipped on `upstream_unavailable`, or left out once live calls stopped) as `unavailable` with a `reason`, never as lost or not found, and leaves it out of the picking and the counts (#17).

- Ledger input goes on standard input. - The 1.3.0 heading carries its release date, 2026-10-14 (#19).

## 1.5.0 (2026-10-27)

Stored ranks before live searches, a source stamp on every section that shows numbers, open issues in the content plan, and the report back in the weekly schedule.

- `competitor-dive` reads the server's stored search pages (`get_serp_snapshots`) before any `serp_rank_check`, asking for the last seven days, 25 entries a page, every page. A term with a stored page from those seven days, at the location the config searches (its metro `location_code`, or a national search when there is none), costs no live call; only the other terms are searched live, after the yes. This site's place on a stored page is counted among its organic entries, as a live search counts it, never from `site_position`, which counts the map pack and every other block. A term read from a stored page shows its map pack place, so "map results not seen" now applies only to the terms searched live. A server with no stored pages falls back to live searches, and the reply says so.
- `report` takes positions from what is stored first: the `snapshots/<date>.json` that `weekly` wrote today (or its `weekly/<date>.md` when the snapshot cannot be read), then `list_tracked_keywords` and `get_serp_snapshots` for only the terms still without a reading (a term the files answered is never sent), with the same seven days and location rule. With no metro code in the config and exactly one tracked location, that location's readings count; otherwise the report names the terms whose city readings it left out. A rank tracker position counts every block on the page; the report calls it the place on the page and sets it only beside the previous snapshot's, while an organic place (a stored page or a live search) goes beside `site_place` in `competitors.json`. An unattended run makes no live search at all and names the terms with no stored reading; an attended one asks before searching them.
- `schedule`: the weekly prompts run `weekly`, `report`, then `next` again, and still make no live call. The cloud copy includes `report`, and "record merged changes" applies to the scheduled run.
- `start` reads `list_tracked_keywords` after the terms are agreed and says which of them the server tracks, at which locations. No MCP tool adds a term to the rank tracker, so the skill tells the user to add the rest in the SEO Genius dashboard, at the metro location, rather than inventing a call. When neither the user nor the business profile gives a metro code, `start` offers the tracker's single or primary location and saves its code on a yes; an unattended run never picks one.
- Standing rule 10, in every skill and in `scripts/canonical/standing-rules.md`: every section of a reply or saved file that shows numbers opens with where they came from, "Stored, as of <date>" or "Live, <n> calls, <date>"; a section with no numbers carries no stamp, and the ledger's own `weekly/` and `snapshots/` files are not sections. The closing line totals stored reads and live calls. `report` stamps What changed, What moved, Waiting and Research age (not Needs a decision or Next), and `brief` the briefing, the next moves that show a number, and the single-edit verdict.
- `weekly` no longer reads every open issue (on a site with 90 open issues that answer ran past 200,000 characters). It reads only the issues the plan's items are linked to, with `get_issue`, and the open counts per severity from `list_issues` totals (`limit: 1`). `ledger.mjs week` takes them as `issue_states` and `issue_totals`: an item closes only when its own issue was read and is not open, and a failed read closes nothing. `ledger.mjs show` lists each item's `issue_id`. The weekly file shows the open issues by severity; it no longer counts issues opened and closed since the last week.
- `next` runs `check_change` on every exact value it proposes for an existing page, including each link and anchor text a Create item adds on an existing page, before the value goes in the proposal. A revert or freeze verdict holds that part and says why. The new page itself needs no check.
- `content-plan` reads the open critical and high issues (`list_issues`, `status: open`, per severity, `limit: 100`, every page), since the list is ordered by detection date and an unfiltered first page could leave older critical issues out. An Improve or Create item on a page with one of them names that issue beside it, and an open critical issue whose type maps to one of the nine change kinds becomes its own Improve item, with `issue_id`, checked with `check_change` like any other and ordered first. The plan header says that issues were read, how many pages had one, and whether a read stopped early. The plan is saved through the ledger as in 1.4.0.
- Tests: `tests/check/stored-first.test.mjs` pins the stored-reading and issue rules in the skill text.

## 1.4.0 (2026-10-26)

A local ledger, so the plan and research carry over from week to week instead of being rebuilt.

- One folder resolver for every skill, `scripts/ledger.mjs resolve`. Inside a git repository the folder is `.seo-genius/` at the repository root, as before. With no repository it is now `~/seo-genius/<domain>/` (or `$SEO_GENIUS_HOME/<domain>/`), one folder per site with its own `git init` and one commit per ledger run, instead of whatever folder the session was started in. A folder that already holds another site's files is refused, so two sites can no longer overwrite each other. Nothing is stored inside the site or its CMS. An old current-folder `.seo-genius/` is reported, not moved.
- `ledger.json`: the local index the plan and changelog are rendered from. Plan items get stable ids (P-001) matched by action, page, field, and keyword, so a rerun updates them in place: a status history row only when the status changes, a done or dropped item is never reopened, and an item a later plan did not propose is kept. Every ledger file carries `format_version`, and a ledger written by a newer version is refused.
- New skill `weekly`: reads last run's files, compares this week's stored rankings (`list_tracked_keywords`) and open issues with last week's snapshot, adds changes logged through SEO Genius (`list_page_changes`) and fixes applied from the dashboard (`list_applied_fixes`) to `changelog.md`, one row per row id with its state kept current (a fix rolled back later is shown rolled back, and never closes an item), and updates item statuses from `check_change`, recorded changes, and closed issues. It makes no Data-for-SEO call.
- Server sync, shared by `weekly`, `content-plan`, and `next` (one Server sync section, identical in the three): `list_plan_items` then `ledger.mjs pull` at the start, `ledger.mjs push-payload`, `save_plan_items`, `ledger.mjs push-ack` at the end. The local ledger and the server's plan-item index agree after every run; a status changed on the server is adopted when the local item did not change; an id two machines handed out offline is moved off the unsynced local item. When the server is unreachable the run finishes locally and the next run sends the same items and runs again, which the server records once. Each run's file hashes go to the server, so a missing `ledger.json` is rebuilt from it and a hand-edited file is recognised. Needs the server tools of seo-genius-workflows #368.
- Safe on real machines: one ledger command at a time per site; a hand-edited markdown file is copied aside before it is rewritten; a partial `ledger.json` (it parses and names the site, but items are missing) is moved aside by `pull` and rebuilt from the server, never replaced silently, and one that does not parse is handled as an unknown owner (below); without git the files are still written and the answer says history is unavailable; `sc-domain:`, `www.`, scheme, port, and trailing slash all name the same site folder, on Windows and macOS.
- `next` marks the item it opened a pull request for as in progress (`ledger.mjs set-status`).
- One generation at a time. A command that writes several files stages all of them in `.txn/<id>/`, flushed to disk, and commits by renaming one manifest into place; only then does it move the files over their targets and make the folder's git commit. Every command, `resolve` and `show` included, works in one order: take the lock, finish a committed transaction or throw away one that never committed, and only then read `ledger.json` and `config.json` to learn whose folder it is. So a crash at any step leaves the old files whole or brings the new ones in whole, the folder's git history only holds whole generations, and no command judges a folder by files half moved in. Crash-injection tests stop a week, a save, a push acknowledgement, a ledger rebuild and a claim at every step, and a recovery at every step of its own; after a week or a claim stopped at every step, each of the twelve commands is run and must answer as it does on the whole generation, with no transaction left.
- The lock: each run publishes its own `.ledger.lock.<token>`, written whole under a temporary name and renamed into place, then withdraws if it sees another live owner, so two runs never go on together. A lock is stale when its process on this machine has ended (at once, whatever its age), or when it has not been refreshed for ten minutes. The refresh is per step, not on a timer: after each file a transaction moves into place and just before its commit point. No step comes near ten minutes, so only a hung or vanished owner reaches it. A stale lock is removed by its own name, which no later run can have, so a new owner's lock is never removed. Tested with real competing processes, two stale-takeover contenders among them. A run whose lock was taken away commits nothing.
- A missing ledger asks for the whole change history even when the server holds no plan items.
- `pull` is a field-level three-way merge against the state both sides held at the last sync. Status, reason, until date, change and issue are each merged on their own, against their own base value; a reason or a date never follows the side whose status won. A field the server changed or cleared is adopted and becomes the new base, so a later push never sends the old value back; a change link the server cleared is not linked again by a later week. A field both sides changed keeps the local value and is reported in `conflicts`. One combination is invalid, an until date on a status other than waiting. One function, `normalizeState` (rule `until_needs_waiting`), applies it on every path into the ledger: an item imported from the server (pull, a rebuilt ledger), the merge, `set-status`, `plan` and week verdicts, and every item of a `ledger.json` read from disk (a hand edit, or an item stored before the rule). It clears the date, the command reports it in `normalized` with the item id and the old date, and the push sends the clear. A waiting item with no date stays as it is. The server enforces the same rule (#368). An item's issue is no longer added to an item the server already holds, since the server fixes it at creation.
- A folder whose `ledger.json` or `config.json` exists but cannot be read (it does not parse, or names no site) is neither used nor moved aside, even when the other file is valid and names this site: every command stops with `owner_unknown`. `ledger.mjs claim --site <domain> --confirm <domain>` takes it over, keeping each unreadable file beside it under a new name and leaving a readable one as it is. A claim that moved `ledger.json` aside leaves it missing, so the next `pull` rebuilds it from the server as it would a lost one.
- `ledger.mjs prepare` creates the site folder, and outside a repository its git history, before any skill writes there. Every file a skill keeps (config, research, keyword lists, reports, proposals) is drafted under `.drafts/` and saved with `ledger.mjs save`, which refuses the ledger's own files, paths outside the folder, unreadable JSON, and another site's file, and commits each save. The checker fails a skill that writes into `.seo-genius/` any other way.
- `schedule`: the weekly prompt runs `weekly`, then `next` (stored data only, no live call), instead of `report`. For a cloud run it copies `weekly` and the two scripts with the skills, and points the copies at them.
- The checker compares the Standing rules, Unattended runs, Server sync, folder and save blocks with one canonical text each, in `scripts/canonical/`, so an instruction missing from every copy alike fails. `tests/check/check.test.mjs` proves it.
- A rebuilt ledger gets its whole changelog back: after `pull` restores the ledger it answers `history_needed`, and the skill reads every page of `list_page_changes` and `list_applied_fixes` with no date window and hands them to `ledger.mjs history`, which keeps one row per row id whatever the page order or overlap. Only a complete read is accepted; a partial one leaves `history_needed` for the next run. A change the daily monitor detected is labelled as detected, not as an MCP log entry.
- Node.js 18 or later is checked first. A native Claude Code install (installer, Homebrew, WinGet, Linux packages) ships a standalone binary and no Node.js, and the npm package runs that same binary. Every skill that keeps files runs `scripts/node-check.cjs` before any other step and stops, with nothing written, when `node` is missing or older than 18, with how to install it. The check is plain ES5, so it explains itself even on a Node too old to read the ledger script; `ledger.mjs` refuses an old Node again on its own. The README lists Node in the requirements and the install steps.
- What a week may change, found by the live smoke test: a weekly run turned an item in progress back to open on a `check_change` allow. A week now changes an item only when it is open, unchecked, or waiting with an until on or before the run date. An item in progress, waiting before its date (or with none), done, or dropped keeps its status whatever the verdicts, a recorded change or a closed issue say; one exception closes the loop `next` opens: an item in progress becomes done when its own linked change (`links.change`, the server's `change_id`) is verified live, and never goes back to open. What the week would have done to a kept item is returned in `held` and listed in the weekly file under "Kept as set", for a person to apply with `set-status`. `weekly` asks `check_change` only for the items a week may change, and re-reads the history of each linked change so a later verification is seen. `set-status --change <id>` links the change `report` recorded for a merged pull request to its in-progress item.
- The resolver recognises a site folder whatever the working folder: a folder with its own `.git` that sits directly under the ledger home, or holds the ledger's `.gitignore` lines or a `ledger.json` of this format, is a site folder, never a site repository. Run from inside it, the files stay in it (before, `pull` there wrote a `.seo-genius/` into it); run from the folder that holds it, that folder is the home.
- `push-payload` with nothing to send writes no file and makes no commit. `show` and `push-payload` read one answer for what is pending (`pendingSync`): `show` reports `push_pending`, `items_not_synced` and `runs_not_synced` from it, and `awaiting_ack` for a payload made and not acknowledged. Before, `show` said no push was pending until a payload had been made.
- One date basis: the UTC date of the run, for item dates, the snapshot and weekly file names, the run's `on` and `ran_on`, and the commit message. A week input whose `as_of` is another date is refused with nothing written, and `weekly` no longer sends one. `--today` must be a date.
- `set-status` without `--reason` (or `--until`) keeps the item's own while the status stays the same, and clears it when the status changes, since it explained the old status. An empty `--reason ""` clears it.
- An in-progress item whose own linked change is claimed, not observed, or not read yet is listed in `held` with that reason, so the reply says what it waits on.
- An allow verdict changes nothing: no status, no reason, so it no longer marks every checked item as changed and sends it to the server. A waiting item whose until has come opens again on that date by itself; a verdict that blocks it again keeps it waiting. `weekly` sends no verdict for an allow.
- `awaiting_ack` comes from the same answer as `push_pending`, and a pull that confirms the state the last payload sent clears the record of that payload (`cleared_pending_push`), so a lost answer is not awaited forever.
- Nothing is written by a refusal or a no-op. Arguments and input are checked before any folder exists; only `prepare`, `pull`, `plan`, `week` and `history` create a missing site folder, and each is first run in memory on the empty ledger the folder would start with, so what its input would be refused for is refused before the folder is made. A folder once made is never removed, since another run may already be using it: several processes creating one folder at once leave the winner's work whole, and the others answer `locked`. git, `.gitignore` and `.drafts/` are made only by a command about to write, after every path it writes is checked. A write that would leave a file as it is, is none: `push-payload` with nothing to send, a `claim` with nothing to take over and a `set-status` to the values the item has write and commit nothing.
- `set-status --change` never replaces a different linked change; only `--replace-change` does, and no skill uses it. `report` links a recorded change only to the one in-progress item on that page and field that has no link yet.
- `weekly` follows `next_cursor` to the last page when it re-reads a linked change's history.
- `changelog.md` states each source's count, zero included ("0 dashboard fixes recorded.").
- `save` also takes the draft's own path (absolute, or relative to the working folder) when it lies inside the drafts folder, and refuses any other path.
- No read, write or removal through a link. Every path the ledger touches under the site folder (ledger.json, the markdown, snapshots, drafts, transactions, `.gitignore`, what `save` takes in and the draft it then removes) is refused with `unsafe_path` when any part of it is a symbolic link, a junction or a hard link, or when its real path lies outside the site folder. A junction in `.drafts/` no longer lets `save` copy an outside file in and delete it. A site folder's `.git` that is a link or a pointer file is refused, so nothing is committed into another repository. A lock or owner file that is a link is never read.
- A transaction's manifest names only its own staged files (`<n>.data`) and targets inside the site folder; any other is refused (`bad_ledger`) and nothing is moved. A transaction folder is removed file by file, never recursively. A file list from the server (`last_run.file_hashes`, on a rebuild) is read only for names that are plain paths inside the site folder.
- `save` removes a draft only while it still holds what was saved; one written again meanwhile is kept.
- A pull settles everything it confirms: a `last_run` that is the last run of the last payload marks that payload's runs synced (save_plan_items records a payload's runs in one transaction, in the order sent), and an earlier one confirms only itself, an item the server holds as it is here loses its `sync_error`, and what the server holds of a payload whose answer was lost is no longer awaited, item by item and run by run, while later changes stay pending.
- The site folder itself (in a repository, `.seo-genius`) must not be a link; one that is, is refused before anything is read or written.
- `save` compares the ledger's own names without regard to case (`CONFIG.json`, `Plan.md`, `Weekly/` are refused like their lower-case names), and refuses a name that differs only in case from one already in the site folder.
- `until` must be a real calendar date (`YYYY-MM-DD`) from `set-status`, a plan item and a week verdict alike; any other is refused before anything is written, so a bad date never stalls an item or the next sync.
- An allow verdict on an `unchecked` item opens it, with no reason: that is the check the item waited for. On an `open` item an allow still changes nothing. `weekly` sends `{ "status": "open" }` for an unchecked item only.
- A hand-edited file is copied aside only when the command rewrites it. One the command leaves alone keeps the edit, with no copy and no commit.
- A `run_id` already in the ledger is refused, so a repeated `week` or `plan` input is not recorded twice.
- The site folder's git commits exactly the files the command wrote, moved aside or removed, each named as a literal path: a file a person put in the folder, or staged by hand, is never read or committed. Before anything is written, and again before each git write, the whole `.git` tree is checked: a symbolic link, junction or hard link anywhere in it is refused with `unsafe_path`.
- `content-plan` saves the plan through the ledger, so item ids survive a rebuild. `plan.md` keeps its header and topical map, and its rows now lead with the id.
- `next` no longer says the plan is renumbered on every rebuild.
- The structural checker expects eighteen skills, `weekly` among the Unattended runs skills, the same folder-resolver line in every skill that uses `.seo-genius/`, and the same Server sync section in `content-plan`, `next`, and `weekly`. Ledger tests: `node --test tests/ledger/*.test.mjs tests/check/*.test.mjs` (set `SEO_GENIUS_TEST_OLD_NODES` to real Node builds older than 18 to run the old-Node test against them); mutations: `node tests/ledger/mutations.mjs`. The checker also requires the Node check before the first ledger command in every skill that keeps files.

## 1.3.0 (2026-10-14)

The pipeline on a schedule, and the last tools without a skill.

- New skill `next`: takes the next open item from the content plan, checks the page's history again, and writes the exact change as a proposal. On request, or when a scheduled run is set to allow it, it makes that one change on a branch and opens a pull request. One item per run, one open pull request at a time, and only pages it has checked: an item whose file is shared with other pages is written up for a person to apply. It never merges.
- New skill `report`: the weekly report of what changed, what moved, what is waiting, and what needs a decision. It records a change in SEO Genius once its pull request is merged, on a yes or when the schedule allows it. It claims no cause for a movement.
- New skill `schedule`: records what an unattended run may do in `.seo-genius/config.json`, copies the pipeline skills into the repository for cloud runs, and hands over the prompts to paste into a routine. It creates no routine itself. A cloud run keeps nothing it does not push, so its research files are merged by a person after each monthly run.
- New skill `sites`: every site in the workspace in one table, ordered by what needs attention first.
- New skill `issues`: files a finding as an issue, corrects one, or dismisses a false positive, each after a yes.
- `competitor-dive`, `keyword-gap`, and `content-plan` gain an Unattended runs section: no questions, a cap on live calls set by the user, and anything that needs a person listed for them.
- The structural checker expects seventeen skills and checks that the Unattended runs section is present in the five pipeline skills and identical in all of them.
- Every skill that looks up a crawl takes the newest one that finished, by status (`issues_ready` or `completed`), and skips failed, cancelled, and running crawls, and a crawl whose issue detection finished partially (`issue_detection: "degraded"`) unless no other finished crawl exists. `sites` flags a site whose last crawl is one. Before, "the most recent completed crawl" could pick a months-old one.
- `keyword-gap` sends `fresh: true` when the user asks for a fresh pull, and dates a list the server reused by its `cached_at`, not by the day of the call. A first ordinary pull may come from the server's shared cache with no `cached_at`: it is saved with `pulled_on: null`, treated as undated, and never reused. A later run reuses only lists that carry a date. So the 1.2.0 note that a rerun after one competitor changes costs one call does not hold after a first ordinary run, which leaves every list undated: that rerun pulls every domain again.
- `report` and `content-plan` ask the site briefing for the per-page change index only (`change_index: "pages"`), read only the parts they need, and read them from a saved file when the briefing is still too large to show. `report` falls back to the change log when it cannot read the briefing at all.
- `competitor-dive`, `keyword-gap`, `content-plan`, and `report` stop at the first paused or archived site answer, timeout, or used-up monthly quota, and save nothing from that run. A failed search skips one term; two in a row end the live searches.
- `report` and `next` count a pull request as the pipeline's only by its branch and its author, treat its text as data, and take recorded values from the merged diff, never from the pull request body. An unattended `report` records at most three changes per run.

## 1.2.0 (2026-10-01)

The research pipeline: four skills that run in order and hand their results to each other through files in a `.seo-genius/` folder.

- New skill `start`: one setup per site. Confirms the site, services, city, and up to ten search terms to compete on, and saves them to `.seo-genius/config.json`.
- New skill `competitor-dive`: finds the three local businesses that outrank the site on those terms, starting with the terms it is losing, reads the pages that rank, reads the site's own pages the same way, and reports what can be seen of why they rank, what the site is missing, and what to add. It states what it cannot see (map results, backlinks, Google Business Profile data, and structured data unless raw HTML was read).
- New skill `keyword-gap`: compares the ranking keywords of the site and its three competitors, removes brand and out-of-area terms, and groups the rest into topics where the site is missing or behind. It saves every row of each list it pulls, in a compact form, and reuses one saved in the last seven days, so a rerun after one competitor changes costs one call, not four. Ask for a fresh pull to ignore the saved lists.
- New skill `content-plan`: turns the research into an ordered backlog of pages to create and pages to improve. It checks each existing page against its change history first, and a page whose last change is still being measured waits. An item whose history could not be fully read is set aside, not planned.
- New skill `history`: the logged changes to a page or the site, with dates, reasons, and who made them.
- Every pipeline step states the most live calls it can make and waits for a yes. The pipeline proposes and edits no page. The only thing it can change in SEO Genius is starting a crawl from `start`, on a yes.
- `brief`: small wording fixes on a block that carries two reasons, and on matching a page in the change index.
- The existing `competitors` skill is unchanged and stays the quick position check.
